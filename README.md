# Task API — Django REST Framework Learning Project

A beginner-friendly REST API for managing tasks, built with Django 5.2 LTS and
Django REST Framework. The API runs on a Rocky Linux 9 VM. Code is edited on
Windows and deployed to Linux via Git.

---

## Compatibility

| Component | Version | Notes |
|---|---|---|
| Python | 3.11 | Installed from Rocky Linux 9 AppStream. Python 3.9 (the RL9 default) reached EOL October 2025 and must not be used. |
| Django | 5.2 LTS | Active LTS, supported until April 2028. Django 4.2 LTS reached EOL April 2026. |
| Django REST Framework | 3.17.2+ | Supports Django 5.2 + Python 3.11. First DRF release patching CVE-2026-73228. |
| psycopg2-binary | 2.9.13 | PostgreSQL 13 adapter. Binary wheel — no C build tools needed on Rocky Linux. |
| PostgreSQL | 13 | Already running on Linux. No upgrade required. |

## Project Structure

```
uttt-poc/
├── .env.example          # Template for environment variables — copy to .env on Linux
├── .gitignore            # Excludes .env, venv/, __pycache__, etc. from Git
├── requirements.txt      # Python packages to install in the virtual environment
├── manage.py             # Django's CLI utility (run migrations, start server, run tests)
│
├── taskapi/              # Django project package (configuration)
│   ├── settings.py       # All Django settings — reads secrets from env vars via python-decouple
│   ├── urls.py           # Root URL routing — maps /api/ to tasks app, /admin/ to Django admin
│   ├── wsgi.py           # WSGI entry point (used by production servers like Gunicorn)
│   └── asgi.py           # ASGI entry point (for async servers — not used in this stage)
│
└── tasks/                # Tasks Django app
    ├── models.py         # Task database model (id, title, description, completed, created_at)
    ├── serializers.py    # Converts Task objects to/from JSON; validates input
    ├── views.py          # TaskViewSet — handles all CRUD HTTP requests
    ├── urls.py           # Registers /api/tasks/ and /api/tasks/{id}/ routes via DefaultRouter
    ├── admin.py          # Registers Task in the Django admin interface
    ├── apps.py           # App configuration (name, default_auto_field)
    ├── tests.py          # Automated tests for create, retrieve, update, delete
    └── migrations/       # Database schema migrations (generated by makemigrations)
        └── __init__.py
```

### How the pieces connect

```
HTTP request
    → Django receives it in manage.py / wsgi.py
    → taskapi/urls.py routes /api/* to tasks/urls.py
    → tasks/urls.py maps the path to TaskViewSet (in views.py)
    → TaskViewSet uses TaskSerializer (serializers.py) to validate input / format output
    → TaskSerializer reads/writes the Task model (models.py)
    → Django translates model operations to SQL via psycopg2 → PostgreSQL
```

## API Endpoints

All endpoints are under `/api/`.

| Method | URL | Action |
|---|---|---|
| GET | `/api/tasks/` | List all tasks |
| POST | `/api/tasks/` | Create a new task |
| GET | `/api/tasks/{id}/` | Retrieve one task |
| PUT | `/api/tasks/{id}/` | Fully update a task (all fields) |
| PATCH | `/api/tasks/{id}/` | Partially update a task (selected fields) |
| DELETE | `/api/tasks/{id}/` | Delete a task |
| GET | `/api/` | API root — lists available endpoints |

### Task fields

| Field | Type | Writable | Notes |
|---|---|---|---|
| `id` | integer | No | Auto-assigned by PostgreSQL |
| `title` | string | Yes | Required, max 200 chars, cannot be blank |
| `description` | string | Yes | Optional, defaults to `""` |
| `completed` | boolean | Yes | Optional, defaults to `false` |
| `created_at` | datetime | No | Set automatically when task is created |

## Linux Setup (Rocky Linux 9)

Run all of the following commands in your Rocky Linux 9 terminal.

### Step 1 — Install Python 3.11

Rocky Linux 9 ships with Python 3.9 as the system default (`python3`). Python 3.9
reached end of life in October 2025. Install 3.11 from the AppStream repository
alongside the system Python — this does **not** replace or remove `python3`.

```bash
sudo dnf install python3.11 python3.11-pip -y
python3.11 --version   # should print Python 3.11.x
```

### Step 2 — Clone or pull the repository

If this is the first time:

```bash
# Replace the URL with your actual Git remote
git clone https://github.com/YOUR_USER/uttt-poc.git
cd uttt-poc
```

If you already have the repository and are pulling new changes:

```bash
cd ~/path/to/uttt-poc
git pull
```

### Step 3 — Create the PostgreSQL database

Connect to PostgreSQL and create the `uttt` database. If your `pg` user is a
PostgreSQL superuser, run:

```bash
psql -h 127.0.0.1 -U pg -c "CREATE DATABASE uttt;"
```

If you get a permission error, connect as the `postgres` OS user first:

```bash
sudo -u postgres psql -c "CREATE DATABASE uttt OWNER pg;"
```

You only need to do this once.

### Step 4 — Create the Python virtual environment

A virtual environment keeps the project's packages separate from the system Python.

```bash
# Create a venv named 'venv' in the project root using Python 3.11
python3.11 -m venv venv

# Activate it — your prompt will change to show (venv)
source venv/bin/activate
```

> **Tip:** You must activate the venv every time you open a new terminal session
> before running `python` or `pip` commands for this project.

### Step 5 — Install Python dependencies

```bash
pip install --upgrade pip
pip install -r requirements.txt
```

This installs Django, Django REST Framework, psycopg2-binary, and python-decouple.

### Step 6 — Create the .env file

```bash
# Copy the example file
cp .env.example .env

# Edit it and fill in your real values
nano .env
```

You need to set at minimum:

- `SECRET_KEY` — generate one with:
  ```bash
  python -c "import secrets; print(secrets.token_urlsafe(50))"
  ```
  Copy the output and paste it as the `SECRET_KEY` value.

- `DB_PASSWORD` — the password for your `pg` PostgreSQL user.

After editing, restrict permissions so only your user can read it:

```bash
chmod 600 .env
```

> **python-decouple** reads `.env` automatically — you do not need to `source`
> or `export` anything. Just having `.env` in the project root is enough.

### Step 7 — Run database migrations

Django uses migrations to create the database tables your models need.
`makemigrations` generates the migration file from `tasks/models.py`.
`migrate` applies it to the database.

```bash
python manage.py makemigrations tasks
python manage.py migrate
```

Expected output from `migrate` ends with lines like:
```
  Applying tasks.0001_initial... OK
```

You only need to run `makemigrations` again if you change `models.py`.

### Step 8 — (Optional) Create an admin superuser

This gives you access to the Django admin UI at `/admin/`.

```bash
python manage.py createsuperuser
```

Follow the prompts to set a username, email, and password.

### Step 9 — Start the development server

```bash
python manage.py runserver 0.0.0.0:8000
```

`0.0.0.0` means "listen on all network interfaces" — required so that VirtualBox
can forward connections from Windows into the VM.

You should see:

```
Django version 5.2.x, using settings 'taskapi.settings'
Starting development server at http://0.0.0.0:8000/
Quit the server with CONTROL-C.
```

## Connecting from Windows via VirtualBox NAT

This section sets up a port-forwarding rule so that `http://127.0.0.1:8000`
on your Windows machine reaches the Django server running on your Linux VM.

### VirtualBox port forwarding

1. Shut down or save-state the VM (the rule can also be added while the VM is
   running in recent VirtualBox versions).
2. In VirtualBox, select your VM → **Settings** → **Network**.
3. Expand **Adapter 1** (should be set to **NAT**).
4. Click **Advanced** → **Port Forwarding**.
5. Click the **+** button to add a new rule:

   | Field | Value |
   |---|---|
   | Name | django |
   | Protocol | TCP |
   | Host IP | 127.0.0.1 |
   | Host Port | 8000 |
   | Guest IP | *(leave blank)* |
   | Guest Port | 8000 |

6. Click **OK** on all dialogs.

### Linux firewall (if firewalld is running)

Rocky Linux 9 runs firewalld by default. Allow port 8000 for the current
session and permanently:

```bash
sudo firewall-cmd --add-port=8000/tcp
sudo firewall-cmd --add-port=8000/tcp --permanent
```

> If you get `FirewallD is not running`, firewalld is disabled on your VM and
> you can skip this step.

### ALLOWED_HOSTS

Your `.env` file must include `127.0.0.1` in `ALLOWED_HOSTS` so Django accepts
requests arriving with that Host header from Windows:

```
ALLOWED_HOSTS=localhost,127.0.0.1
```

This is already the default in `.env.example`.

## Testing the API from Windows

With the Django server running on Linux and port forwarding in place, open a
terminal on Windows (Command Prompt, PowerShell, or Git Bash).

### Using curl

**List all tasks (empty at first):**
```
curl http://127.0.0.1:8000/api/tasks/
```

**Create a task:**
```
curl -X POST http://127.0.0.1:8000/api/tasks/ ^
     -H "Content-Type: application/json" ^
     -d "{\"title\": \"Buy groceries\", \"description\": \"Milk and eggs\"}"
```

*(In Git Bash or PowerShell, replace `^` line continuation with backtick `` ` ``
or just put the whole command on one line.)*

**Retrieve a single task (replace 1 with the actual id):**
```
curl http://127.0.0.1:8000/api/tasks/1/
```

**Mark a task as completed (PATCH updates only the fields you send):**
```
curl -X PATCH http://127.0.0.1:8000/api/tasks/1/ ^
     -H "Content-Type: application/json" ^
     -d "{\"completed\": true}"
```

**Delete a task:**
```
curl -X DELETE http://127.0.0.1:8000/api/tasks/1/
```

### Using the browser

Because `BrowsableAPIRenderer` is enabled in `settings.py`, you can explore the
API interactively in a browser:

- API root: `http://127.0.0.1:8000/api/`
- Task list: `http://127.0.0.1:8000/api/tasks/`
- Single task: `http://127.0.0.1:8000/api/tasks/1/`

## Important: Development Server Limitations

The command `python manage.py runserver` starts **Django's built-in development
server**. This is appropriate for learning and local testing only.

It is **not suitable for production** because:
- It handles only one request at a time (no concurrency)
- It has no security hardening
- It restarts itself on code changes (which can be disruptive under load)
- It does not handle HTTPS

When you are ready to deploy persistently, you will need:
- A production WSGI server such as **Gunicorn** (`pip install gunicorn`)
- A reverse proxy such as **Nginx** in front of it
- A process manager (systemd service or supervisor) to keep it running

Those steps will be added in a later stage of this project along with Jenkins
CI/CD automation.
